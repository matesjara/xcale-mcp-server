# Autocore Hotels — grill notes (provider)

- **Last modified:** 2026-11-13
- **Status:** resolved, and observed against Staging end to end — payments included (2026-11-13,
  `sandbox-evidence.md`). Only the webhook is unobserved, and it is the consumer's (it never reaches this server). The
  consumer half has its own grill: `xcale-backend/docs/design/autocore-gateway/grill-notes.md` (matesjara/xcale-backend#2915).
- **Code target repo:** `xcale-mcp-server` (this provider). Consumer: `xcale-backend` Payment Request layer
  (matesjara/xcale-backend#1068, `src/modules/payment-requests/gateways/port.ts`, `IPaymentGatewayPort`).
- **Issue:** matesjara/xcale-mcp-server#188 · **First tenant:** Bio Habitat (matesjara/xcale-backend#2074)
- **Docs:** https://docs-api-dev.autocore.pro/ · **Template:** the Wompi provider (`docs/design/wompi-provider/`).
- **Evidence:** [`sandbox-evidence.md`](./sandbox-evidence.md) (Staging, hotel 5, 2026-11-09).

> Autocore Hotels is a payment platform for hotels in Colombia and Costa Rica: hosted payment links (card, PSE,
> Nequi, Daviplata, SINPE Móvil, gift cards, preloaded balances), a direct-charge virtual terminal, and booking flows
> over the RoomCloud channel manager. This provider exposes only its payment links, as a second gateway behind
> Payment Request.

---

## 1. Decisions

| #    | Question                      | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| :--- | :---------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-1  | v1 scope                      | Payment links only: `check_credentials` (probe, `GET /v2/hotels`), `create_payment_link` (`POST /v2/links/schedule/`), `deactivate_payment_link` (`DELETE /v2/bookings/chatbot/<code>`), `get_transaction_status` (`GET /v2/common/transaction-status`). All `controlPlane`. Out: Direct Charge (card data, PCI), refunds (fast-follow), the open link (`POST /v2/links/open-schedule/`), Bookings/RoomCloud (a separate provider, when a RoomCloud hotel exists), Gift Cards, Virtual Cards, Preloaded Balances. `gift_cards` / `preloaded_balance` as payment options pass through `allowed_payment_options`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| D-2  | Deactivating a link           | Autocore's docs do not document it, but its web app's "Cancelar cobro" calls `DELETE /v2/bookings/chatbot/<code>`, and the same call with our `Auth-Token` answers `200` `"Reserva cancelada correctamente"` — also on a link already cancelled (idempotent). Afterwards the status read gives `cancelled` and the checkout refuses the link (`400` "Estado: Cancelado") (observed). So v1 has `mcp_autocore_deactivate_payment_link`, like Wompi's, and the consumer's `deactivateLink` works as the port expects. A paid link cannot be cancelled: `404` "El estado de pago actual no permite la cancelación", the payment untouched (observed 2026-11-13) — the tool answers `PROVIDER_ERROR` and the consumer re-reads the status.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| D-3  | Credential and auth           | Both keys are secret: one composed credential `access_key:secret_key` (the WooCommerce `ck:cs` precedent, ADR 0018), delivery `reference` (financial provider, ADR 0003 / ADR 0010). **Autocore authenticates only with the `Auth-Token`** — base64(`access_key;ts;sha256_hex(secret_key + ts)`), valid 30 s; the plain `access_key` / `secret_key` headers return 401 (observed). The token is computed per HTTP request by a new core auth variant, the only place the secret is revealed — the CTO's decision and its ADR (`docs/adr/`). Rejected: `access_key` as public context like Wompi's `publicKey` (it is half of the credential; nothing is gained by exposing it).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| D-4  | Confirming a payment          | **MCP:** a per-link status read, `GET /v2/common/transaction-status` with `transaction_type=payment_link` and `ref_number` = the link's `code` (observed; our `external_ref_id` there is a 404). The consumer's `findTransactions(linkIds)` is one read per pending link. `create_payment_link` takes a generic `notificationUrl` and `externalRef` (provider vocabulary, no consumer concepts). **Backend:** receives the webhook (`temp_webhook_url`) and never trusts it alone — it confirms with the status read before settling (the webhook is unsigned). **Rejected:** the DLM listing by hotel (`/v2/transactions/vouchers/hotel/{id}`): Autocore keeps the last-request timestamp server-side, so a retry, a probe or a second consumer consumes the window (breaks stateless and consumer-agnostic); it also returns guest and card data.                                                                                                                                                                                                                                                                                                                                                                    |
| D-5  | Environment per connection    | A context field `environment: 'staging' \| 'production'`, chosen by the tenant at connect, **no default**. The provider alone maps it to the base URL (`https://api-stg.autocore.pro` / `https://api.autocore.pro`); the consumer passes the tenant's choice, never Autocore knowledge. Keys are per environment (Staging keys return 401 on `api-dev`, observed), and Staging is what Autocore issues to integrators; Testing (`api-dev`) is Autocore's own. Account identity: `accountContextKeys: ['hotelId', 'environment']`. Rejected: a per-deployment base URL (one deployment serves both); probing both environments (it guesses).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| D-6  | Amount and currency           | The tool takes Autocore's unit: `amount`, a positive integer in **major units** (a `150000` link shows $150.000 COP, observed), said so in the field description. Autocore accepts a fractional amount, so the integer schema is what refuses one; the consumer converts `amountMinor` → major units and refuses a fraction (never rounds money). `currency`: an ISO 4217 three-letter code, **required** by the tool although Autocore defaults it. **Autocore does not check the currency against the hotel's** (a `CRC` link was created for a COP/USD hotel, observed), so the probe returns the hotel's currencies and the consumer checks before creating — the provider makes no extra call per link. No minimum is enforced upstream (a `$100` link was created).                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| D-7  | Guest data                    | Autocore requires only `guest_name` (and `amount`): `email` is optional (observed; the docs say required). The tool requires `guestName`; `email`, `phone` and `countryCode` are optional. The provider never fabricates them. The checkout collects the payer's own data itself (person type, document, contact). **For the backend's grill (CPO + CTO):** the port's `CreateLinkInput` gains an optional buyer, and only its name is needed for Autocore; where the name comes from when the agent does not have it is a product call there. Rejected: a placeholder name or email (false data to a third party that moves money).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| D-8  | The rest of the link's fields | The provider passes the tenant's choices through and decides none. v1 input: `description` (required by the tool — it is the concept the checkout shows — although Autocore accepts none), `externalRef` (required), `notificationUrl` (required), `availableHours` (integer ≥ 1; the consumer converts the port's `expiresAt` rounding **down**), `allowedPaymentOptions` (optional, the documented enum; absent or empty = the hotel's own setup; Autocore does not check it against the hotel's services, observed), `installments` (optional), **`sendLinkByEmail` (required, no default)** — Autocore emails the guest unless told not to, so no consumer can do it by omission. The backend takes its value from a tenant setting that ships **off** (tenant-autonomy › Defaults; the CPO confirms in the backend grill). Out of v1 (additive later): `redirect`, `reservation_id`, `booking_dates`, `source` (Autocore fills the account's own, `xcale`, observed; required only for an account with several).                                                                                                                                                                                                  |
| D-9  | The connection probe          | `mcp_autocore_check_credentials` calls `GET /v2/hotels` (creates nothing) and checks that the context's `hotelId` is among the hotels the keys reach — the listing is scoped to the keys (observed: one hotel). It pages by `offset` / `limit` until `total_items`, with a hard cap (`links.next` points past the end even on the last page, observed). Found → `ok({ valid: true, hotel: { id, name, currencies, primaryCurrency } })` — the name lets the consumer show the account, the currencies feed D-6; nothing else of the hotel's record (phone, legal name, commissions) leaves the provider. Not found → `PROVIDER_INVALID_INPUT`, own message — a reconnect does not fix a wrong id. Bad keys → 401 → `PROVIDER_AUTH_EXPIRED`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| D-10 | What the status read returns  | The consumer's settlement compares asked vs paid (`settle-payment-request.usecase.ts:81-87`, `mismatch`). `transaction-status` carries stable codes but no amount; the link's own record (`GET /v2/links/schedule/<code>`, without `validate_link_status`) carries the amount paid per transaction but only Spanish labels. So `mcp_autocore_get_transaction_status` reads the status and, **only when `applied`**, the link record, taking the amount and the link's currency from the payment whose `transaction_id` is the status's. Output: `code`, `externalRef`, `status`, `transactionId`, `occurredAt` (the payment's `created_at`, naive UTC at Autocore), `amount`, `currency` — the last four null unless applied. `""` and `"N/A"` (a declined attempt) mean no transaction. `status` is Autocore's `status_code` as sent. Payer data dropped. An `applied` status without a readable payment is an error, never "paid, amount unknown". The documented voucher is not used: `voucher_url` is a PDF and `/v2/transactions/vouchers/detail` answers `400` "No se pudo determinar el ambiente" (observed). A `rejected` link is not closed ("Reintentar Pago"); a paid link cannot be paid again (observed). |
| D-11 | Errors                        | Status → `ProviderErrorCode` by the core's policy (401/403 → `PROVIDER_AUTH_EXPIRED`, 400/422 → `PROVIDER_INVALID_INPUT`, 429 → `PROVIDER_RATE_LIMITED`, 5xx/network → `PROVIDER_UNAVAILABLE`, 404 and the rest → `PROVIDER_ERROR`). Own messages, `Autocore <operation> failed (HTTP n)`. Autocore's errors are `{ code: 0, message, detail }` with free Spanish text in `detail` and no stable code; they did not echo a key (observed), and the provider still never propagates `detail` (redaction test).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| D-12 | Creating is not idempotent    | Autocore accepts a repeated `external_ref_id` and creates a second link (observed), and a link cannot be looked up by it. The provider **never retries** the `POST` (a timeout is `PROVIDER_UNAVAILABLE`, and a payable link may exist). The consumer does not retry blindly either; a payment on a link whose response was lost still reaches it by webhook with its `externalRef`, which is how it recognises its own.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| D-13 | Public reads at Autocore      | `transaction-status` answers without the `Auth-Token`, and `GET /v2/links/schedule/<code>` — what the checkout loads — is public and returns the guest's name, email and phone (observed). Anyone with a link's code, which travels in the URL the guest receives, can read them. The provider still authenticates every call and never logs a link's URL or code beyond what an outcome returns. Reported to Autocore; how much guest data to send is the consumer's to weigh (D-7).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| D-14 | The account's `source`        | Autocore requires `source` on every create since 2026-11-13 (`400` "Debe indicar el origen…" without it). It is the account's origin, handed over with the keys (xcale's is `xcale`), so it is a required **context** field (routing data, not a secret) that the create sends. Not part of the account identity (`accountContextKeys` stay `hotelId` + `environment`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

## 2. Resolved by the evidence

- 2026-11-09 spike: P-2 (only the `Auth-Token`), P-3 (`ref_number` is the link's `code`), P-4 (major units), P-5
  (`email` optional), P-6 (the hotel listing is scoped to the keys).
- 2026-11-13 payments: P-1 (a paid link cannot be paid again; cancelling it has no effect) and P-7 (`applied`,
  `rejected` with `"N/A"`, `pending`, `cancelled`; the amount from the link record). Not observed: `in_process` (the
  pending cards were not read while confirming) and the webhook (the consumer's QA).
