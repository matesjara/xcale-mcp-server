# Autocore Hotels — grill notes (provider)

- **Status:** resolved for the provider, pending evidence (P-1 – P-7). The consumer half (gateway adapter, webhook
  ingress, buyer data, the email setting) gets its own grill in `xcale-backend`.
- **Date:** 2026-10-29
- **Code target repo:** `xcale-mcp-server` (this provider). Consumer: `xcale-backend` Payment Request layer
  (matesjara/xcale-backend#1068, `src/modules/payment-requests/gateways/port.ts`, `IPaymentGatewayPort`).
- **Issue:** matesjara/xcale-mcp-server#188 · **First tenant:** Bio Habitat (matesjara/xcale-backend#2074)
- **Docs:** https://docs-api-dev.autocore.pro/ · **Template:** the Wompi provider (`docs/design/wompi-provider/`).
- **Sandbox:** Testing credentials requested from Autocore by email (2026-10-29); not received. No contract until the
  wire facts below are observed.

> Autocore Hotels is a payment platform for hotels in Colombia and Costa Rica: hosted payment links (card, PSE,
> Nequi, Daviplata, SINPE Móvil, gift cards, preloaded balances), a direct-charge virtual terminal, and booking flows
> over the RoomCloud channel manager. This provider exposes only its payment links, as a second gateway behind
> Payment Request.

## 1. Decisions

| #    | Question                      | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| :--- | :---------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-1  | v1 scope                      | Payment links only: `check_credentials` (probe, `GET /v2/hotels`), `create_payment_link` (`POST /v2/links/schedule/`), `get_transaction_status` (`GET /v2/common/transaction-status`). All `controlPlane`. Out: Direct Charge (card data, PCI), refunds (fast-follow), Bookings/RoomCloud (a separate provider, when a RoomCloud hotel exists), Gift Cards, Virtual Cards, Preloaded Balances. `gift_cards` / `preloaded_balance` as payment options pass through `allowed_payment_options`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| D-2  | Deactivating a link           | No endpoint in the docs. v1 is designed without deactivation and says so: no invented tool; the consumer's `deactivateLink` reports it cannot; the tenant's lever is a short expiry (`available_hours`). Changing the port is the backend CTO's call, after Autocore answers. **P-1.**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| D-3  | Credential shape              | Both keys are secret: one composed credential `access_key:secret_key` (the WooCommerce `ck:cs` precedent, ADR 0018), delivery `reference` (financial provider, ADR 0003 / ADR 0010). The wire scheme only changes materialization — and **either scheme touches the core**: `api_key` places one secret in one header, so two headers from one composed secret is a small declarative extension, and the `Auth-Token` (a hash of the secret and a timestamp, valid 30 s) is the first imperative auth variant, which `CONTEXT.md` says needs its own variant and an ADR. Rejected: `access_key` as public context like Wompi's `publicKey` (in the header scheme it travels beside the secret; nothing is gained by exposing it). **Awaiting Autocore's confirmation — P-2.**                                                                                                                                                                                                   |
| D-4  | Confirming a payment          | **MCP:** a per-link status read, `GET /v2/common/transaction-status` (`transaction_type=payment_link`, `ref_number` = the link's code — **P-3**); the consumer's `findTransactions(linkIds)` is one read per pending link. `create_payment_link` takes a generic `notificationUrl` and `externalRef` (provider vocabulary, no consumer concepts). **Backend:** receives the webhook (`temp_webhook_url`) and never trusts it alone — it confirms with the status read before settling (the webhook is unsigned). **Rejected:** the DLM listing by hotel (`/v2/transactions/vouchers/hotel/{id}`): Autocore keeps the last-request timestamp server-side, so a retry, a probe or a second consumer consumes the window (breaks stateless and consumer-agnostic); it also returns guest and card data.                                                                                                                                                                            |
| D-5  | Environment per connection    | A context field `environment: 'testing' \| 'production'`, chosen by the tenant at connect, **no default**. The provider alone maps it to the base URL (`api-dev.autocore.pro` / `api.autocore.pro`); the consumer passes the tenant's choice, never Autocore knowledge (unlike the Wompi prefix mapping that was moved out of the consumer). Staging (`api-stg`) out of v1 — an additive enum value if Autocore says integrators must use it. Account identity: `accountContextKeys: ['hotelId', 'environment']` (hotel 17 in Testing and in Production are two connections). Rejected: a per-deployment base URL (one deployment serves both); probing both environments (it guesses).                                                                                                                                                                                                                                                                                         |
| D-6  | Amount and currency           | The tool takes Autocore's unit: `amount`, an integer in **major units** (whole pesos), said so in the field description (Fidelity over Unification; Wompi's `amountInCents` was Wompi's unit). The consumer's adapter converts `amountMinor` → major units and **refuses** an amount with a fraction (never rounds money silently). `currency`: an ISO 4217 three-letter code, not fixed to COP (`sinpe_movil` means Costa Rica, CRC; each hotel carries its own currency). The provider does not check it against the hotel's currency: Autocore's rejection maps to `PROVIDER_INVALID_INPUT`. No minimum is documented; if one exists, the consumer adds its agent-facing reason once known. **Major units inferred — P-4.**                                                                                                                                                                                                                                                  |
| D-7  | Guest data Autocore requires  | The tool requires what Autocore requires: `guestName` and `email`; `phone` and `countryCode` (ISO 3166-1 alpha-2) optional. The provider never fabricates them. **For the backend's grill (CPO + CTO):** the port's `CreateLinkInput` has no buyer (the record keeps only `origin.buyerPhone`, `entities.ts:39`); it gains an optional buyer (`name`, `email`, `phone`) that Wompi ignores and Autocore needs, and where the email comes from (the agent asks the guest; the reservation, e.g. Cloudbeds) is a product call there. Rejected: a placeholder email (false data to a third party that moves money; receipts would land in our mailbox). **P-5.**                                                                                                                                                                                                                                                                                                                   |
| D-8  | The rest of the link's fields | The provider passes the tenant's choices through and decides none. v1 input: `description` (required), `externalRef` (required), `notificationUrl` (required), `availableHours` (integer ≥ 1; the consumer converts the port's `expiresAt` rounding **down**, so a link never outlives its request), `allowedPaymentOptions` (optional, the documented enum: `nequi`, `daviplata`, `pse`, `credit_card`, `sinpe_movil`, `preloaded_balance`, `gift_cards`; absent = the hotel's own setup), `installments` (optional), **`sendLinkByEmail` (required, no default)** — Autocore emails the guest unless told not to, so no consumer can do it by omission (provider knowledge, not policy). The backend takes its value from a tenant setting that ships **off** (tenant-autonomy › Defaults; the CPO confirms in the backend grill). Out of v1 (additive later): `redirect`, `reservation_id`, `booking_dates`, `source`.                                                       |
| D-9  | The connection probe          | `mcp_autocore_check_credentials` calls `GET /v2/hotels` (creates nothing) and checks that the context's `hotelId` is among the hotels the keys reach, paging (`offset` / `limit`) with a hard cap. Found → `ok({ valid: true, hotel: { id, name, currency } })` (the consumer shows the name so a wrong account is visible; the currency feeds D-6; nothing personal). Not found → `PROVIDER_INVALID_INPUT`, own message — not `AUTH_EXPIRED`, since a reconnect does not fix a wrong id. Bad keys → 401 → `PROVIDER_AUTH_EXPIRED`. **Assumes the listing is scoped to the keys — P-6.**                                                                                                                                                                                                                                                                                                                                                                                        |
| D-10 | What the status read returns  | The consumer's settlement compares asked vs paid (`settle-payment-request.usecase.ts:81-87`, `mismatch`), and `transaction-status` carries no amount. So `mcp_autocore_get_transaction_status` reads the status and, **only when `applied`**, the voucher (`GET /v2/transactions/vouchers/detail?transaction_id=…`) for `amount` and `currency`. Output: `linkCode`, `externalRef`, `status`, `transactionId`, `occurredAt`, `amount`, `currency` (the last two null unless applied). `status` is Autocore's `status_code` as sent, a plain string (Fidelity; the consumer's adapter maps applied→approved, rejected/invalid_card→declined, pending/in_process→pending, cancelled→voided, error→error). Payer data (`guest`, `card_holder`, masked card) is dropped. An `applied` whose voucher cannot be read is an error, never "paid, amount unknown". Rejected: assuming the link's amount (the mismatch check could never fire); the webhook's amount (unsigned). **P-7.** |
| D-11 | Errors (mirrors Wompi)        | Status → `ProviderErrorCode` by the core's policy (401/403 → `PROVIDER_AUTH_EXPIRED`, 400/422 → `PROVIDER_INVALID_INPUT`, 429 → `PROVIDER_RATE_LIMITED`, 5xx/network → `PROVIDER_UNAVAILABLE`, 404 and the rest → `PROVIDER_ERROR`). Own messages, `Autocore <operation> failed (HTTP n)`; Autocore's `detail` never reaches an outcome or a log (whether it echoes a key is unobserved — the rule holds regardless, with a redaction test). A 404 from the status read is not read as "rejected" until P-7 is observed.                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

## 2. Pending

### Asked to Autocore (2026-10-29), awaiting their answer

- **P-1** Does a link close by itself after an approved payment, or can it be paid twice? Is there a way to void or
  expire a link before its expiry?
- **P-2** Which auth do Payment links and Transactions use: the `access_key` + `secret_key` headers, or the
  `Auth-Token`? Does `transaction-status` require auth? Either answer is a core change (D-3); the `Auth-Token` one
  needs an ADR and the CTO's review (`/implement` does not merge core changes alone).
- **P-5** Is `email` required on a payment link even with `send_link_by_email: false`?

### To verify in Testing once the keys arrive

- **P-3** `ref_number` of `transaction-status` is the `code` returned by `POST /v2/links/schedule/` (hints: the
  unauthenticated 404 says "Link de pago no identificado"; the refund path uses `{payment_link_code}`).
- **P-4** `amount` is in major units: create a `150000` COP link and read the amount on the checkout page.
- **P-6** `GET /v2/hotels` lists only the hotels the keys reach, not every Autocore hotel. If it lists all, the
  probe's hotel check proves nothing and needs another per-hotel read.
- **P-7** What `transaction-status` returns for an unpaid link (`pending` or `404`), and that its `transaction_id`
  reads the voucher detail.

## 3. Observed (Testing, `api-dev.autocore.pro`, unauthenticated, 2026-10-29)

- `GET /v2/hotels`, `POST /v2/links/schedule/` and `GET /v2/bookings/availability` →
  `401 {"code":0,"message":"Error http: 401","detail":"Credenciales inválidas"}`, identical with fake
  `access_key`/`secret_key` headers, a fake `Auth-Token` and a malformed one: the scheme cannot be told from errors.
- `GET /v2/common/transaction-status?hotel_id=1&ref_number=x&transaction_type=payment_link` with no credentials →
  `404 {"code":0,"message":"Error http: 404","detail":"Link de pago no identificado"}`.
- The server is uvicorn; `/docs` and `/redoc` are public.
